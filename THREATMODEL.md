# faxios threat model

This document describes the threat model for faxios: a library used at runtime by millions of applications, and an open-source project with a build pipeline, release infrastructure, and human maintainers.

It is for maintainers, security researchers, and downstream consumers doing supply chain due diligence. If you find a gap, open a security advisory rather than a public issue.

---

## 1. Scope and methodology

We model two distinct systems:

| System             | What is being protected                     | Who attacks it                                                    |
| ------------------ | ------------------------------------------- | ----------------------------------------------------------------- |
| Runtime            | Applications that `import faxios`            | Malicious servers, network attackers, malicious application input |
| Project / SDLC     | The integrity of what gets published to npm | Supply-chain attackers, phishers, malicious contributors          |

For each system, we list assets, trust boundaries, threat actors, and threats, rated by likelihood x impact. When mitigations exist in the codebase, we cite the file. When they do not, we say so. Runtime source paths (`lib/...`) are relative to `packages/lib/src/`; every other path is relative to the repository root.

The runtime model is general by design. faxios is a transport library and cannot know what its callers consider sensitive. The project model is specific and actionable.

## 2. Runtime threat model

### 2.1 System overview

```
  ┌─────────────────┐
  │  Application    │  ← trusted: writes the config, owns the secrets
  │  (caller code)  │
  └────────┬────────┘
           │ faxios(config)
  ┌────────▼────────┐
  │  Config merge   │  ← lib/core/mergeConfig.ts
  │  Header build   │  ← lib/core/FaxiosHeaders.ts
  ├─────────────────┤
  │  Middleware     │  ← caller-supplied code (.use()), runs in-process
  ├─────────────────┤
  │  URL build      │  ← lib/core/resolveRequestURL.ts, lib/core/buildFullPath.ts, lib/helpers/buildURL.ts
  │  Adapter        │  ← lib/adapters/fetch.ts (web-standard fetch, all runtimes)
  └────────┬────────┘
           │
  ═════════▼═════════  ← TRUST BOUNDARY (network)
           │
  ┌────────▼────────┐
  │  Origin server  │  ← UNTRUSTED in the general case
  └─────────────────┘
```

### 2.2 Assets

| Asset                          | Why it matters                                               |
| ------------------------------ | ------------------------------------------------------------ |
| Credentials in transit         | `config.auth`, `Authorization` headers, cookies, XSRF tokens |
| Request/response bodies        | May contain PII, business secrets                            |
| The caller's process integrity | Prototype pollution can lead to RCE in some downstream gadgets |
| The caller's internal network  | SSRF can pivot through the host running faxios                |
| Availability                   | Oversized responses, slow-loris responses                    |

### 2.3 Trust boundaries

1. Caller to faxios. The caller is fully trusted. Anything the caller passes in `config` is assumed intentional. faxios does not defend against a malicious caller; that is a non-goal.
2. faxios to network. Everything past the socket is untrusted: response status, headers, body, redirect `Location`. faxios no longer follows redirects itself; the underlying `fetch` runtime handles redirects and applies its own cross-origin credential rules. Proxy handling is likewise delegated to the runtime (e.g. undici), not managed by faxios.
3. Caller-supplied hooks to faxios internals. `.use()` middleware and plugins, `transformRequest`, `transformResponse`, `paramsSerializer`, and a custom `env.fetch` run with full process privilege. faxios does not sandbox them. A middleware sees and can change every request's config (including `Authorization`), can read every plugin's `ctx.capabilities`, can replace the response, and can call `next` more than once.

### 2.4 Threat actors

| Actor                         | Capability                                                                                                           |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Malicious server              | Controls every byte of the response. Most common.                                                                    |
| On-path network attacker      | MITM. Mitigated by TLS unless the caller disabled validation.                                                        |
| Malicious redirect target     | A trusted server redirects to an attacker. The attacker sees whatever faxios forwards.                                |
| Application user              | Controls part of the request (e.g. a URL path segment, a query param, a header value) via the calling application.   |

### 2.5 Threats

> Severity = Likelihood x Impact, rated for a typical server-side deployment. Browser deployments inherit the browser's same-origin policy and are generally lower risk for SSRF and credential leakage.

#### T-R1: SSRF via caller-controlled URL

|                   |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | Application interpolates user input into `config.url` or `config.baseURL`. Attacker supplies `http://169.254.169.254/`, `http://localhost:6379/`, `file://`, `gopher://`, etc.                                                                                                                                                                                                                                                                                                                 |
| **Likelihood**    | **High.** This is the #1 real-world faxios misuse pattern.                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Impact**        | **High.** Cloud metadata theft, internal service access.                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **In scope?**     | **Partially.** faxios cannot know which URLs the caller intends to allow.                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Mitigations**   | • On an instance with a `baseURL`, `allowAbsoluteUrls` defaults to `false` and an absolute `url` rejects with `ERR_INVALID_URL` before fetch (`lib/core/resolveRequestURL.ts`, `lib/core/buildFullPath.ts`), so an attacker-supplied absolute URL cannot redirect the request to another host. Set `allowAbsoluteUrls: true` only for trusted URLs. <br>• The fetch adapter only speaks the schemes the `fetch` runtime accepts (`http:`/`https:`/`file:`/`blob:`/`data:`); exotic schemes like `gopher:` are rejected. <br>• No built-in host allowlist. Callers must validate destinations themselves. |
| **Residual risk** | Substantial. This is documented as caller responsibility.                                                                                                                                                                                                                                                                                                                                                                                                                                      |

#### T-R2: Credential leakage on cross-origin redirect

|                   |                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | Caller sends a credential (`Authorization: Bearer …`, or a custom header such as `X-Api-Key`) to `https://api.trusted.com/x`. Server responds `302 Location: https://evil.com/`. Does the credential go to evil.com? |
| **Likelihood**    | Medium                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **Impact**        | High (full credential theft)                                                                                                                                                                                                                                                                                                                                                                                                             |
| **In scope?**     | **Partially.** faxios no longer follows redirects itself. The custom Node redirect handling (`follow-redirects`, `beforeRedirect`, `maxRedirects`, `sensitiveHeaders`) was removed with the http adapter. Redirect following is delegated entirely to the underlying `fetch` runtime (browser, undici, Deno, Bun), which applies the WHATWG Fetch cross-origin credential-stripping rules. `authBearer` and `authenticate` are in scope for the headers, cookies and query parameters they set. |
| **Mitigations**   | • The `fetch` runtime strips `Authorization`, and only `Authorization`, on cross-origin redirects per the WHATWG Fetch spec. Any other header (`X-Api-Key`, `Cookie` set by hand) is sent to the redirect target. <br>• `authBearer` with a custom `header` (anything other than `Authorization`) sets `fetchOptions.redirect` to `"error"` unless the request sets `redirect` itself, so a redirect rejects with `ERR_NETWORK` and the header never reaches another host. `authenticate` does the same for every header but `Authorization`, for its cookies, and for its query parameters; both share that code (`lib/plugins/credentials.ts`). Query parameters refuse redirects because `forwardTo` copies the full URL, query string included, into a header, and fetch forwards every header but `Authorization` on a redirect. <br>• Callers needing manual control can set `redirect: 'manual'` via `fetchOptions` and inspect the `Location` themselves. |
| **Residual risk** | Low for `Authorization` and for the headers, cookies and query parameters `authBearer` and `authenticate` set. A custom secret header set by hand, or an `authBearer` or `authenticate` request whose caller sets `redirect: "follow"`, goes to the redirect target; use `redirect: "error"` or `"manual"` for those, since faxios no longer offers `sensitiveHeaders`. |

#### T-R3: Header injection (CRLF)

|                   |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | Application puts user input into a header value: `headers: { 'X-User': req.query.name }`. Attacker supplies `foo\r\nX-Injected: bar\r\n\r\n<body>`. A related surface is multipart per-part headers: attacker-controlled `blob.type` or `blob.name` flowing into the multipart body.                                                                                                                                                                                                                              |
| **Likelihood**    | Low                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Impact**        | Medium to High (request smuggling, response splitting, multipart parser confusion)                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Mitigations**   | • `lib/core/FaxiosHeaders.ts` strips CR, LF and the other C0 control characters except tab, and DEL, from every header value it stores (`lib/helpers/sanitizeHeaderValue.ts`), so `foo\r\nX-Injected: bar` goes out as the single value `fooX-Injected: bar`. The fetch adapter (`lib/adapters/fetch.ts`) then reduces each value to a ByteString before it builds the `Request`. The runtime's `Headers` rejects an invalid header name or value (WHATWG Fetch), so such a request fails before anything is sent. Tests: `packages/tests/unit/axiosHeaders.test.ts`, `packages/tests/unit/adapters/fetch.test.ts`. <br>• faxios does not validate header names itself. A string passed to `headers.set(name, value)` that is not a valid header name is parsed as raw header lines, so an untrusted `name` there can add headers. <br>• faxios writes no multipart bytes. A `FormData` body, including one `toFormData` builds, is encoded by the runtime: by `fetch`, or by `new Request(...)` when faxios counts the body for `onUploadProgress` or `maxBodyLength` (`buildUploadStream` in `lib/adapters/fetch.ts`). Escaping of field names, file names and types in per-part headers is the runtime's multipart/form-data encoder's. A `form-data` package body is rejected (`lib/core/dispatchRequest.ts`). The Axios `formDataToStream` escaping (GHSA-445q-vr5w-6q77) no longer exists because faxios has no multipart encoder of its own. |
| **Residual risk** | Very low for header values (faxios strips CR/LF, and the runtime's `Headers` rejects any that reach it). A caller that passes an untrusted header name to `headers.set()` must validate it. Multipart per-part headers depend on the runtime's `FormData` encoding, which faxios does not control. |

#### T-R4: Prototype pollution, write side (polluting response / merge into a target object)

|                   |                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | Server returns `{"__proto__": {"isAdmin": true}}`. If faxios merged this into an object naively, every `{}` in the process would gain `.isAdmin`.                                                                                                                                                                                                                                                  |
| **Likelihood**    | Low (requires a downstream gadget to be exploitable)                                                                                                                                                                                                                                                                                                                                              |
| **Impact**        | High (process-wide state corruption, sometimes RCE)                                                                                                                                                                                                                                                                                                                                               |
| **Mitigations**   | • `JSON.parse` itself does not pollute (it creates own-properties named `__proto__`, not prototype links). <br>• Internal merge and copy paths skip the dangerous keys `__proto__` / `constructor` / `prototype` through the one `isDangerousKey` check in `lib/utils.ts`: `merge` in `lib/utils.ts`, `lib/core/mergeConfig.ts`, `lib/core/cloneConfig.ts`, `lib/helpers/formDataToJSON.ts`, and the header, plugin-option and capability copies in `lib/core/Faxios.ts`. `params` keep every own key, because they are caller data for the query string, stored as data slots on a null-prototype object (`ownCopy` in `lib/core/mergeConfig.ts`). <br>• `FaxiosHeaders` (`lib/core/FaxiosHeaders.ts`) skips the header names `__proto__` / `constructor` / `prototype`, and `lib/helpers/parseHeaders.ts` parses raw headers into a null-prototype object. <br>• The built-in `authBearer`, `authenticate` and `forwardTo` plugins (`lib/plugins/credentials.ts`, `lib/plugins/forwardTo.ts`) copy `ctx.config` (and `forwardTo` its `env`, `authenticate` the request's `params`) into null-prototype objects. <br>• Tests: `packages/tests/unit/utils/merge.pollution.test.ts`, `packages/tests/unit/utils/extend.pollution.test.ts`, `packages/tests/unit/core/mergeConfig.pollution.test.ts`, `packages/tests/unit/core/FaxiosHeaders.pollution.test.ts`, `packages/tests/unit/helpers/formDataToJSON.test.ts`, `packages/tests/unit/helpers/parseHeaders.test.ts`. <br>• These were added in response to past advisories. A regression here is a P0. |
| **Residual risk** | Low, but this is an area of active attacker interest. New merge helpers must go through the same filtering.                                                                                                                                                                                                                                                                                       |

#### T-R4b: Prototype pollution, read-side gadgets (polluted `Object.prototype` drives faxios behavior)

|                   |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | A _different_ library in the caller's dependency tree pollutes `Object.prototype` (e.g. `Object.prototype.validateStatus = () => true`). faxios code that reads a config property through the prototype chain then picks up the attacker's value and executes the associated behavior. Each reachable property is a distinct **gadget**: `validateStatus` (bypass HTTP error handling), `parseReviver` (silently tamper JSON response bodies), `withXSRFToken` (leak XSRF token cross-origin), `transformResponse` (response replacement), and so on. The former `transport` / `httpAgent` / `lookup` MITM gadgets are gone with the http adapter, but the gadget class remains for every config-read path.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Likelihood**    | Low to Medium (requires a polluted prototype somewhere in the process, historically common).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Impact**        | High. Arbitrary behavior change across every faxios call (auth bypass, response tampering, credential leakage). Unlike T-R4, this does not require faxios itself to pollute; any polluted process is enough.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| **Mitigations**   | Config reads that can drive behavior see only own properties, so polluted prototype properties are not read: <br>• `lib/core/mergeConfig.ts`: per-prop reads from `config1`/`config2` guarded with `hasOwnProp`; `mergeDirectKeys` (used by `validateStatus`) uses `hasOwnProp` rather than the `in` operator which traverses the prototype chain (fix for GHSA-w9j2-pvgh-6h63). The merged config is a null-prototype object. <br>• `lib/defaults/index.ts`: the default `transformResponse` reads `responseType` and `parseReviver` with `hasOwnProp` (fix for GHSA-3w6x-2g7m-8v23), and runs with the null-prototype merged config as `this`. <br>• `lib/core/resolveRequestURL.ts` reads `baseURL`, `url`, `allowAbsoluteUrls` and the other URL inputs as own properties, so `Object.prototype.baseURL` cannot redirect a relative request. <br>• `lib/core/prepareRequest.ts` copies the config into a null-prototype object (`lib/core/cloneConfig.ts`) and reads `withXSRFToken`, the XSRF names, `headers` and `fetchOptions` as own properties. `withXSRFToken` must be exactly `true` to send the header cross-origin; non-boolean truthy values (`1`, `"false"`, `{}`) no longer short-circuit the same-origin check (fix for GHSA-xx6v-rp6x-q39c). <br>• `lib/adapters/fetch.ts` reads the size limits and progress callbacks from that null-prototype copy, and `env.fetch` / `env.Request` / `env.Response` and `fetchOptions` keys as own properties only; the former http-adapter gadget set (`transport`, `httpAgent`, `httpsAgent`, `lookup`, `family`, `http2Options`) no longer exists, and passing those keys rejects with `ERR_BAD_OPTION` (`lib/core/assertRequestConfig.ts`). <br>• The built-in plugins read their options through `own()` (`lib/plugins/shared.ts`), and `use()` reads a plugin's `middleware`, `provides` and option declarations as own properties (`lib/core/Faxios.ts`). <br>• Regression tests for the gadget class: `packages/tests/unit/prototypePollution.test.ts` (both unit-level and end-to-end against `faxios.get`), and the `*.pollution.test.ts` files under `packages/tests/unit/` (`core/`, `utils/`, `adapters/fetch/`, `transformResponse.pollution.test.ts`). |
| **Residual risk** | Low, but the surface is every config property read. Any new code path that reads `config.foo` / `this.foo` / destructures from a merged config must use a `hasOwnProp` guard. The non-goal that faxios does not defend a caller with a polluted prototype is narrower than it sounds. The pollution typically comes from a transitive dependency, not from the caller's own intent, and the above mitigations neutralize the reachable gadgets even when the prototype is polluted.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

#### T-R5: Oversized / decompression-bomb response

|                   |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | Server sends an enormous body, or `Content-Encoding: gzip` with a 10 KB body that the `fetch` runtime decompresses to 10 GB.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Likelihood**    | Low                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Impact**        | Medium (DoS, OOM kill of the calling process)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Mitigations**   | • `maxContentLength` bounds the response body size, enforced chunk-by-chunk on the fetch response stream in `lib/adapters/fetch.ts`, and up front for `data:` URLs. <br>• `maxBodyLength` bounds the request side, measured from the body itself, never from a caller-declared `Content-Length`. <br>• Both default to `-1` (unlimited). Callers handling untrusted servers should set these. `packages/docs/pages/misc/security.md` documents the mitigation snippet. Tests: `packages/tests/unit/adapters/sizeLimits.test.ts`. <br>• Content-encoding decompression is performed by the `fetch` runtime, which streams; the faxios size guard reads the decoded stream incrementally so memory is bounded by the limit, not the full expansion. |
| **Residual risk** | Medium when limits are not configured. The defaults favor compatibility over safety; the reasoning is that tightening the default would silently break every legitimate download larger than whatever cap were chosen.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

#### T-R6: TLS validation bypass

|                   |                                                                                                                                   |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | Caller configures the `fetch` runtime to skip TLS validation (e.g. a custom undici dispatcher with `rejectUnauthorized: false`, or `NODE_TLS_REJECT_UNAUTHORIZED=0`) to "fix" a certificate error in dev, and ships it to prod. faxios no longer accepts `httpsAgent`; this is now configured at the runtime/fetch level. |
| **Likelihood**    | Medium (very common copy-paste anti-pattern)                                                                                      |
| **Impact**        | High (silent MITM)                                                                                                                |
| **In scope?**     | **No.** faxios delegates TLS entirely to the `fetch` runtime / the browser. We do not inspect or warn on runtime TLS configuration. |
| **Mitigations**   | None at the faxios layer. Documentation responsibility only.                                                                       |
| **Residual risk** | High, but explicitly out of scope. This is caller misconfiguration, not an faxios vulnerability.                                   |

#### T-R7: XSRF token sent cross-origin

|                   |                                                                                                                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | Browser deployment. `xsrfCookieName` is set; attacker tricks the app into requesting `https://evil.com`, or an open redirect on the app's own origin sends a same-origin request on to `https://evil.com`, and the XSRF token cookie value is attached as a header. `fetch` drops only `Authorization` when a redirect leaves the origin. |
| **Likelihood**    | Low                                                                                                                                                                                   |
| **Impact**        | Medium                                                                                                                                                                                |
| **Mitigations**   | `lib/core/prepareRequest.ts` only attaches the XSRF header when `isURLSameOrigin()` passes for the resolved URL (`baseURL` included), or when `withXSRFToken` is exactly `true` (own property, or a resolver returning `true`). This was the fix for **CVE-2023-45857**. When it attaches the header and the request sets no own `fetchOptions.redirect`, it sets `redirect: "error"`, so a redirect rejects instead of carrying the token to another origin. `withCredentials` has no effect on the header. |
| **Residual risk** | Low. The same-origin check uses the WHATWG `URL` parser (`lib/helpers/isURLSameOrigin.ts`), which is robust against parser-differential attacks. A caller that sets `fetchOptions.redirect: "follow"` on an XSRF-bearing request, or forces `withXSRFToken: true`, sends the token wherever the redirect or URL points. Same-origin redirects are also refused under the default, which breaks an app that relies on them until it sets `redirect` itself. |

#### T-R8: Sensitive data in error objects

|                   |                                                                                                                                                                                                                                                                                                    |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | Request fails. `FaxiosError` includes `config`, which includes `config.auth` and `config.headers.Authorization`. Caller logs the error, exposing secrets in logs.                                                                                  |
| **Likelihood**    | **High**                                                                                                                                                                                                                                                                                           |
| **Impact**        | Medium to High                                                                                                                                                                                                                                                                                     |
| **Mitigations**   | `FaxiosError.toJSON()` (`lib/core/FaxiosError.ts`) never includes the request or response, replaces the values of the `authorization`, `proxy-authorization`, `cookie` and `auth` keys (case-insensitive, at any depth, including inside what a value's own or class `toJSON` returns) with `[REDACTED ****]`, and strips `user:pass@` from `url` and `baseURL` and, in linear time, from `message`, `stack` and cause messages. A `redact` array adds keys; a request's list adds to the instance's (`lib/core/mergeConfig.ts`). `config.data` on the error is the caller's body, not the serialized string the adapter sent (`lib/core/dispatchRequest.ts` passes that separately), so `redact` masks body keys for JSON and urlencoded bodies alike. Schema `issues` keep only `message` and each path segment's `key` (`lib/core/validateSchema.ts`), so a library's rejected `input`/`value` is dropped. `timing` reports a failure as `{ code, message, status }`, strips user info from its `url` and its `message`, so its events carry no config. The live error object still carries the full config by reference. |
| **Residual risk** | Medium. `JSON.stringify(err)` and `timing` events are safe by default for the standard credential keys; secrets under other keys (an `X-Api-Key` header, a token in `params` or a field in `data`) need `redact`. A body the caller serialized itself (a string) is logged as it is, and the text of an error message beyond URL user info is the thrower's (a middleware, transform or schema message can carry a secret). Structured loggers that walk object graphs instead of calling `toJSON()` (Winston, Pino with serializers, Sentry) capture `err.config` unredacted unless they configure redaction. |

#### T-R10: Malicious middleware / plugin

|                   |                                                                                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Description**   | Caller installs a third-party faxios plugin from npm whose middleware exfiltrates every `Authorization` header, or calls another plugin's capability (e.g. `ctx.capabilities.auth.getToken()`). |
| **Likelihood**    | Low to Medium                                                                                                                                          |
| **Impact**        | High                                                                                                                                                   |
| **In scope?**     | **No.** Middleware is caller-supplied code running in the caller's process. faxios provides the hook; vetting what goes into it is the caller's job. |
| **Residual risk** | Out of scope, but worth documenting: there is no meaningful difference between `api.use(evil)` and `require('evil')`. Two behaviours callers should know: a middleware that returns without calling `next` hands back a response that never went through `responseSchema`, and one that calls `next` again resends the request, including non-idempotent methods. The built-in `retry` plugin only does that for idempotent methods unless its `methods` option adds others. |
| **Guarantees**    | faxios still filters `__proto__`/`constructor`/`prototype` from plugin `provides`, keeps `ctx.config`, `ctx.state`, `ctx.capabilities` and every dispatched config copy null-prototype, and rejects an abort that lands before the adapter call without sending the request, however long a middleware awaits. Regressions here are security bugs. |

#### T-R11: Form-data recursion DoS (deeply nested input)

|                   |                                                                                                                                                                                                                                                                                                                                                                             |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**   | Caller passes untrusted object input as request `data` in a context that serializes to `multipart/form-data` or `application/x-www-form-urlencoded`. A pathological input with thousands of nesting levels causes `lib/helpers/toFormData.ts` (which `lib/helpers/toURLEncodedForm.ts` also uses) to recurse until stack overflow or the process is killed.                                                                     |
| **Likelihood**    | Low (requires the caller to serialize attacker-controlled object input without validation)                                                                                                                                                                                                                                                                                  |
| **Impact**        | Medium (DoS, stack overflow / process termination)                                                                                                                                                                                                                                                                                                                          |
| **Mitigations**   | • `formSerializer.maxDepth` caps recursion depth; default is 100, can be set to `Infinity` to disable. <br>• Exceeding the cap throws `FaxiosError` with code `ERR_FORM_DATA_DEPTH_EXCEEDED` rather than crashing the process. <br>• Documented in `packages/docs/pages/advanced/multipart-form-data-format.md` and `packages/docs/pages/advanced/x-www-form-urlencoded-format.md`. Tests: `packages/tests/unit/toFormData.test.ts`.            |
| **Residual risk** | Low when callers leave the default in place. Setting `maxDepth: Infinity` reintroduces the risk.                                                                                                                                                                                                                                                                            |

### 2.6 Explicit non-goals (runtime)

faxios will not:

- Sandbox or validate caller-supplied functions (middleware and plugins, transforms, a custom `env.fetch`, serializers).
- Validate that `config.url` points somewhere "safe." We don't know what safe means for your application.
- Warn when TLS validation is disabled via a custom agent.
- Redact `config` from thrown errors. The caller may legitimately need it for retry logic.
- Defend against a fully compromised caller process (e.g. attacker-controlled code running inside the caller). For the narrower case of a polluted `Object.prototype` arriving via a transitive dependency, faxios does defend the reachable config-read gadgets (see T-R4b), but any new config-read path must continue to use `hasOwnProp` guards to stay on this side of the line.
- Defend against monkey-patched JavaScript or Node.js runtime APIs (`Object.keys`, `http.request`, `ClientRequest.prototype.setHeader`, `fetch`, etc.). If attacker-controlled code is already running in the same process, it can observe or alter requests below faxios and this is outside faxios' security boundary.

## 3. Project / supply chain threat model

This model protects what gets published as `@gcmdev/faxios` on npm. A successful attack here compromises every downstream consumer at once. Given faxios' install base, this is the higher-risk half of the document.

### 3.1 System overview

```
  ┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
  │  Maintainer's    │    │  Contributor's   │    │  GitHub.com      │
```

Release artifact flow (#270). `release.yml` calls `run-ci.yml` on the commit it releases. Its build job installs with `--ignore-scripts`, builds, and straight away packs the tarball once with `npm pack --ignore-scripts` and records the file name, version and SHA-256 as job outputs. Only the install, the snapshot version step (on an `rc` run) and the build run before the pack. Lint, the Markdown sync check, the unit, docs-example and browser suites and the docs build all run after it, so a lint, test or docs tool that changes the `.tgz` afterwards fails the publish job's SHA-256 check. The smoke and module jobs test that same file. The `publish` job then downloads the artifact, checks it against those outputs (exactly one file, the SHA-256, `@gcmdev/faxios@<version>` in its `package.json`, `package/LICENSE` present) and runs `npm publish <tarball> --provenance`. It checks out nothing and installs nothing from the repository: the only install is the pinned npm (`npm install -g npm@11.15.0 --ignore-scripts`), which runs no lifecycle scripts. So no repository code and no project dependency runs in the job that holds the OIDC token; that npm release does. The checksum travels as a job output, not inside the artifact, so a replaced artifact fails the check. The `release` job runs bumpy afterwards to tag the commit and publish the GitHub release; bumpy's `publishCommand` for the package (`.bumpy/_config.json`) only confirms the version is on npm. The `rc` path is the same: a manual run of `release.yml` on `main` with `rc` checked has `run-ci.yml` pack main's pending release as `<next version>-rc-<short sha>`, and the `rc` job publishes that tested tarball to the `next` dist-tag.

### 3.2 Assets

| Asset                                 | Compromise means…                                                                                                                        |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| **The npm `@gcmdev/faxios` package name** | Attacker can publish malware as the next `@gcmdev/faxios` version. Game over for the ecosystem.                                       |
| **npm publish capability**            | Whether via token, OIDC trust, or account takeover.                                                                                      |
| **GitHub `adrianbrowning/faxios` write access** | Attacker can merge a Version Packages PR, which triggers publish. Or modify `release.yml` itself.                                 |
| **Maintainer GitHub accounts**        | Transitively grants the above.                                                                                                           |
| **Maintainer workstation secrets**    | SSH keys (GitHub push), `~/.npmrc` token if present (direct publish), GPG keys (signed commits), cloud creds (lateral movement).         |
| **Build determinism**                 | If `packages/lib/dist/` doesn't match `packages/lib/src/`, a backdoor can hide in the built output.                                      |
| **Runtime dependency integrity**      | The runtime dependency surface is minimal; the former `follow-redirects`, `form-data`, `proxy-from-env`, and `https-proxy-agent` deps were removed with the http adapter (fetch-only migration). |

### 3.3 Trust boundaries

1. Contributor PRs to main branch. PRs from forks are untrusted. CI runs them, but `pull_request` workflows have no access to secrets and use a read-only `GITHUB_TOKEN`.
2. Main branch to release. Merging an ordinary PR into `main` only creates or updates the Version Packages PR. Merging that PR publishes, after `run-ci.yml` passes on the merged commit. Both publishing paths in `release.yml` start from a job that requires `github.ref == 'refs/heads/main'`, and `release.yml` has no `pull_request` trigger. Those guards live in the workflow file, so a branch with write access can drop them (see T-S6). Publishing runs only the workflow file already merged to `main` once the `npm-publish` environment admits only `main`, a repository setting that has to be applied by hand. Pushing a tag publishes nothing: bumpy creates the tag after the publish.
3. GitHub Actions to npm. This boundary is crossed via OIDC (`id-token: write` to npm trusted publisher). Only the `publish` and `rc` jobs in `release.yml` request it for npm; both run in the `npm-publish` environment, check out and build nothing, and install only the pinned npm (`npm install -g npm@11.15.0 --ignore-scripts`). The build and test jobs run with `contents: read` and no OIDC. The Pages deploy job in `docs.yml` also gets an OIDC token, for `deploy-pages`, in the `github-pages` environment; npm rejects that token once the trusted-publisher binding names the `npm-publish` environment, an npm setting that has to be applied by hand. The repo has no long-lived `NPM_TOKEN` secret.
4. Maintainer workstation to everything else. This is the softest boundary. A maintainer's laptop is a high-value, low-assurance environment. See §3.5.

| **Likelihood**  | **High** (attempts are constant on high-profile repos)                                                                                                                                                                                                                                                                                                                                                                                                                 |

GitHub does not let a PR author approve their own PR, so the maintainer's own PRs merge through the admin bypass with no second review. Two-person review on sensitive paths remains unavailable until a co-maintainer is added. Path-scoping is pre-staged for that event. |

#### T-S2: Compromised dev dependency steals maintainer keys

> Historically the weakest link. The project-level `.npmrc` and hardware-backed maintainer keys materially improve it, but build-tool plugin execution (`zshy`/Vitest/ESLint) is still the top residual investment area. `ignore-scripts` does not affect those tools, and they run whenever a maintainer builds or tests.

|                            |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description**            | One of the ~45 direct dev dependencies, or one of their thousands of transitive dependencies, is compromised (maintainer account takeover, expired domain re-registration, the usual). It ships a `postinstall` script that reads `~/.npmrc`, `~/.ssh/id_*`, `~/.config/gh/hosts.yml`, `~/.aws/credentials`, `~/.gnupg/` and POSTs them to an attacker. <br><br>The next time a maintainer runs `npm install` on their workstation, the script runs as the maintainer's user, with full filesystem access. No exploit needed. This is npm working as designed. |
| **Likelihood**             | Medium and rising. This exact pattern has hit `event-stream`, `ua-parser-js`, `coa`, `rc`, `node-ipc`, `@solana/web3.js`, the Ledger connect-kit, the 2024 polyfill.io incident, and dozens more. faxios' dev tree includes `zshy`, ESLint, Vitest, and Playwright, each pulling hundreds of transitives. The attack surface is enormous and refreshes on every `npm install`.                                                                                                                                                                                   |
| **Impact**                 | Critical. A stolen npm token with publish rights means direct malware publish. A stolen SSH key with GitHub push rights means a change on `main`, then publish via CI. Either path ends the same way.                                                                                                                                                                                                                                                                                                                                                                     |
| **Current mitigations**    | • CI is protected: `run-ci.yml` installs with `pnpm install --frozen-lockfile --ignore-scripts`, so a malicious lifecycle script cannot execute during the release build. The build runs with a read-only token and no OIDC, and the `publish` job that holds the OIDC token installs no project dependency (only the pinned npm (`npm install -g npm@11.15.0 --ignore-scripts`)): it publishes the tarball CI tested (see §3.1). <br>• CI uses OIDC, not a stored token. There is no `NPM_TOKEN` secret in GitHub for a malicious workflow step to steal. <br>• `pnpm-lock.yaml` pins versions and integrity hashes. A new malicious version won't arrive silently, only on explicit update. `pnpm-workspace.yaml` also holds back releases younger than three days (`minimumReleaseAge`), rejects trust downgrades (`trustPolicy: no-downgrade`) and fails an install when a dependency with a build script is not listed in `allowBuilds` (`strictDepBuilds: true`). <br>• Project-local `.npmrc` sets `ignore-scripts=true`, so `pnpm install` in a contributor or maintainer checkout does not execute lifecycle scripts (`preinstall`, `install`, `postinstall`, `prepare`) from any direct or transitive dependency. <br>• faxios declares no lifecycle scripts of its own. The git hooks in `.husky/` are installed by running `pnpm exec husky` once after install (`CONTRIBUTING.md`).                                                                     |
| **Gaps: workstation**      | `ignore-scripts=true` neutralizes the lifecycle-script path, but it does not neutralize build-time code execution. A malicious `zshy` / ESLint / Vitest plugin still runs when a maintainer executes `pnpm run build` / `pnpm test` / `pnpm run lint`. Those are not lifecycle scripts; they are tools the maintainer explicitly invoked. <br><br>The lockfile pins which packages install, but if one of those pinned packages was already malicious when the lock was generated, or the maintainer runs `pnpm update` / `pnpm add <new-pkg>` without re-setting `ignore-scripts`, fresh lifecycle scripts can land. <br><br>The development environment still has full read access to every credential the maintainer's user can read once a build tool runs. Isolation (devcontainer / VM) remains the strongest control.                                                                                                                                      |

Mitigations adopted and recommended. Adopted items are enforced via the repo; others depend on per-maintainer discipline.

1. Don't keep a publish-capable npm token on your workstation.
   Publishing happens via GitHub Actions OIDC (`release.yml`). Versions 0.1.0 to 0.2.1 were published by hand from a workstation; no release after them needs `npm publish` from a laptop. If `~/.npmrc` has a token, it should be read-only or scoped to unrelated packages. If there is nothing to steal, this attack path is defanged.

2. Run `pnpm install` with lifecycle scripts off locally. Adopted: project ships a `.npmrc` with `ignore-scripts=true`.
   Every `pnpm install` in a contributor or maintainer checkout skips lifecycle scripts by default. To set up git hooks after install, run the one trusted script manually:

   ```
   pnpm exec husky
   ```

   The minor inconvenience of manually running known-good post-install steps is the price of not running thousands of unknown ones. Contributors adding a new dev dependency must not override this flag.

3. Develop in an isolated environment.
   A devcontainer, VM, or sandbox profile that does not have:
   - `~/.ssh/` mounted (use a separate deploy key or SSH agent forwarding only when pushing)
   - `~/.npmrc` with publish tokens
   - `~/.config/gh/` with a `repo`-scoped GitHub token
   - `~/.aws/`, `~/.config/gcloud/`, etc.

   The dev environment should be able to read/write the repo working tree and reach the network for tests. Nothing else.

4. Use hardware-backed keys for GitHub. Adopted project-wide.
   All maintainers use FIDO2/WebAuthn for GitHub auth and `sk-ssh-ed25519@openssh.com` for git push. A stolen `~/.ssh/id_ed25519_sk` is useless without the physical key. This converts "steal a file" into "steal a file and a physical object." Each maintainer should keep a backup key registered and stored separately.

5. Audit lockfile diffs on dependency-update PRs as carefully as code.
   A large `pnpm-lock.yaml` diff hides a lot. Tooling: `npm diff`, `lockfile-lint` (run on every lockfile change by `.github/workflows/lockfile-lint.yml`), Socket.dev's PR integration. Pay particular attention to new packages with install scripts: with `strictDepBuilds: true`, one has to be added to `allowBuilds` in `pnpm-workspace.yaml`, so that diff is the place to look.

6. Don't add dev dependencies casually.
   Each one is a recurring trust decision delegated to a stranger. Prefer tools that can run via `npx` on demand (not in `node_modules`) or that are already in the tree.

| **Description** | The published tarball contains a `dist/` build that does not match what `zshy` would produce from `packages/lib/src/`. Built output is easy to skim past in review. #### T-S6: Workflow file tampering

|                 |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Description** | Attacker with write access (or a merged PR that was not reviewed carefully) modifies `.github/workflows/release.yml` to `curl` the OIDC token somewhere, or to add a step that patches `dist/` after the build.                                                                                                                                                                                                                                                                                                                           |
| **Likelihood**  | Low                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| **Impact**      | Critical                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Mitigations** | • All actions are pinned to full commit SHAs, not tags: `actions/checkout@3d3c42e5… # v7.0.1`, not `@v7`. A compromised action tag can't silently change behavior. <br>• `permissions:` are set per job and minimal. Only the `publish` and `rc` jobs in `release.yml` have `id-token: write` for npm. | **Gaps**        | • Single-maintainer constraint (see T-S1): with one owner, the path-scoped rule cannot enforce a second reviewer on workflow changes. The rule surfaces the sensitivity but does not block single-maintainer approval. Closing this requires adding a co-maintainer. <br>• Publishes go live directly (no npm staged publishing). Required reviewers on the `npm-publish` environment are a repository setting, not a file; without them, a tampered workflow that reaches a publish job publishes without a human approval step. <br>• The `github.ref == 'refs/heads/main'` guards live in `release.yml` itself, so anyone who can push a branch (write access) can remove them on that branch and run the edited workflow there with `workflow_dispatch`. Tags no longer trigger publishing; bumpy creates them after it publishes.                                     |
| **Likelihood**  | Low (requires write access; assumed compromised at that point)                                                                                                                                                                                                                                      |
| **Impact**      | High                                                                                                                                                                                                                                                                                                 |
| **Mitigations** | • npm rejects re-publishing an existing version. Re-tagging cannot overwrite a published version. <br>• Provenance attestation records the commit SHA the release was built from, which is forensically verifiable. Consumers can confirm with `npm audit signatures` (documented in SECURITY.md). <br>• Tag protection rules: repository setting must forbid tag deletion and force-push for the `@gcmdev/faxios@*` pattern (and the older `v*` tags). This is a GitHub UI setting (Settings > Tags > rulesets), not file-based; enforcement is auditable via the Rulesets REST API. |
| **Gaps**        | A new malicious version is still publishable by anyone who can merge to `main`: the publish goes live without a human approval step on npm. This collapses back into T-S1 and T-S3 (review and account security).                                                                                                                                  |

### 3.6 Summary: project risk posture

| Threat                       | Likelihood | Impact       | Current Posture | Priority Gap                                                          |
| ---------------------------- | ---------- | ------------ | --------------- | --------------------------------------------------------------------- |
| T-S1 Malicious PR            | High       | Critical     | Good         | Second maintainer to enable two-person review on scoped paths         |
| T-S2 Dev-dep steals keys     | Medium     | Critical     | Partial      | Isolated dev environment (devcontainer/VM); no publish tokens on workstations. Lifecycle scripts now blocked via project `.npmrc`, but build-tool plugins still execute |
| T-S3 Phishing                | High       | Critical     | Good         | Document phish-response runbook; require registered backup hardware key |
| T-S4 Runtime dep compromise  | Low        | Critical     | Good         | -                                                                     |
| T-S5 Build tampering         | Low        | Critical     | Adequate     | Eliminate build non-determinism, then promote reproducibility check to blocking |
| T-S6 Workflow tampering      | Low        | Critical     | Good         | Second maintainer (two-person review) for `/.github/workflows/`       |

| T-S8 Typosquat               | High       | Medium       | Out of scope | -                                                                     |

The top remaining investment is T-S2 (dev-dependency compromise of maintainer workstations). Lifecycle-script execution is now blocked by the project-level `.npmrc`, and T-S3 phishing risk dropped materially once all maintainers moved to hardware-backed WebAuthn. Real-time credential relay no longer works. The residual T-S2 gap is build-tool plugin execution (`zshy`/Vitest/ESLint), which `ignore-scripts` does not cover. Closing it requires running builds in an isolated environment without access to long-lived credentials.

### 3.7 Incident response runbook

If a maintainer suspects credential compromise (phish clicked, lost hardware key, unexpected tag/publish, leaked token in logs), execute the steps below in order. Speed matters more than completeness. A published malicious version affects every downstream consumer.

#### 1. Contain, minutes 0 to 15

- GitHub: revoke all active sessions (`https://github.com/settings/sessions`), revoke all OAuth/PAT tokens (`/settings/tokens`, `/settings/applications`), review authorized SSH keys and remove any unrecognised. If a PAT with `repo` or `admin:org` scope existed, assume leak.
- npm: run `npm token list` and `npm token revoke <token>` for any publish-capable token. If no CLI access, revoke via `https://www.npmjs.com/settings/<user>/tokens`. Rotate npm password and force sign-out of all sessions.
- Workstation: if a build/install ran malicious code, assume full-user compromise of the laptop. Unplug from trusted networks. Do not rely on AV; move to a clean machine for rotation steps.

#### 2. Assess, minutes 15 to 60

- Check `https://github.com/settings/security-log` for each maintainer account, and the repository's collaborators, deploy keys, rulesets and environments (`https://github.com/adrianbrowning/faxios/settings`), for unrecognised events (key adds, permission changes, force-pushes, new tags).
- Verify recent tags match intent: `git log --tags --oneline -n 20`. Compare with `https://www.npmjs.com/package/@gcmdev/faxios?activeTab=versions`.
- For each recent publish, verify provenance: `npm view @gcmdev/faxios@<version> dist.attestations` and `npm audit signatures` in a project that installs it, and cross-check the `sourceCommit` in the provenance attestation against the tag's SHA. Divergence = investigate.
- Review `~/.npmrc`, `~/.ssh/`, `~/.config/gh/hosts.yml`, `~/.gnupg/` for tampering and unexpected files.

#### 3. Rotate, hour 1 to 4

- Generate new SSH keys on clean hardware. Remove old keys from GitHub. If using `sk-ssh-ed25519@openssh.com`, register new hardware key first, then deregister the old one. Do not leave the account with zero registered keys.
- Re-enrol WebAuthn authenticators (both primary and backup). Deregister lost/compromised authenticators.
- Rotate GPG keys if signed commits are used; upload new key to GitHub.
- Rotate any cloud credentials (`~/.aws/`, `~/.config/gcloud/`) and any tokens present on the compromised machine.

#### 4. Notify, hour 1 onward

- npm security: `security@npmjs.com`. Include package name, suspected versions, timeline.
- GitHub security: `https://github.com/contact`, Security category. Request an investigation of the account.
- Downstream: open a GitHub security advisory (`https://github.com/adrianbrowning/faxios/security/advisories/new`) as soon as a malicious version is confirmed published. Do not wait for a fix. Users need to pin away from the bad version.
- Co-maintainers (when present): notify via out-of-band channel (phone/Signal), not through the compromised channel.

#### 5. Unpublish / deprecate, hour 1 to 24

- npm allows `npm unpublish <pkg>@<version>` within 72 hours of publish. After that, use `npm deprecate <pkg>@<version> "<reason>"` with a message pointing to the advisory.
- Publish a patched version that bumps semver above the malicious one, so `^` consumers move forward automatically.

#### 6. Post-mortem, within 1 week

- Write up timeline: initial vector, dwell time, scope, mitigations applied.
- Update this threat model if the incident reveals a gap not captured here.
- File a PR if any mitigation can be codified (new CI check, new lint rule, new CODEOWNERS path).

Keep this runbook current. A runbook no one has rehearsed is a document, not a control.
