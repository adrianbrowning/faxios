# Pre-Release Changelog

## Unreleased

### Breaking Changes

- **Static helpers are typed only on the default export:** `FaxiosInstance` no longer declares `Faxios`, `CanceledError`, `Cancel`, `isCancel`, `isFaxiosError`, `FaxiosError`, `FaxiosHeaders`, `VERSION`, `toFormData`, `formToJSON`, `all`, `spread`, `mergeConfig`, `HttpStatusCode` or `default`. Only the default export ever had them at runtime, so `faxios.create().isCancel(err)` type-checked and then threw. They now live on the new `FaxiosStatic` type, which is the type of the default export. Use the default export or the named exports (`isCancel`, `all`, …). (**#100**)
- **`paramsSerializer.encode` now takes and returns `string`:** `ParamEncoder` is typed `(value: string, defaultEncoder: (value: string) => string) => string` instead of `unknown` in and out. Runtime behavior is unchanged. Encoders that returned a non-string always produced `"undefined"` or `"[object Object]"` in the query string, and they are now type errors. Migration: return a string from your encoder, e.g. `encode: (v, d) => d(v)` or `encode: encodeURIComponent`.
- **Request `headers` are strictly typed, with autocomplete:** `headers` on every request config, method alias, `create()`, `define()` and `route()` is now `FaxiosConfigHeaders` instead of `Record<string, unknown>`. It accepts a flat header bag, method header groups (`common`, `get`, `post`, …), both mixed in one object, or a `FaxiosHeaders` instance. Editors suggest common header names and `Content-Type` values, and any other name or MIME string is still accepted. Header values must be `string`, `number`, `string[]`, `boolean`, `null` or `undefined`; objects and functions are now type errors. Runtime behavior is unchanged. Migration: convert other values yourself, e.g. `"X-Id": String(id)`. `FaxiosConfigHeaders`, `RawFaxiosRequestHeaders` and `HeadersDefaults` are now exported, `Location` is no longer a suggested request header, and `CreateFaxiosDefaults` is now the same type as `FaxiosRequestConfig`.
- **`defaults` is typed with its real shape:** `faxios.defaults` and the `defaults` of every `create()` instance were typed `{ headers: Record<string, unknown> } & Record<string, unknown>`, so `faxios.defaults.headers.common["Authorization"] = token` failed strict TypeScript with `'...common' is of type 'unknown'`. `defaults` is now the request config with `headers` typed as `HeadersDefaults` (`common` plus one header group per method) and any other key a header value, which applies to every method. `defaults.headers.common[...]`, `defaults.headers.post[...]`, `defaults.headers["X-Name"]`, `defaults.timeout` and `defaults.baseURL` type-check without casts. Runtime behavior is unchanged. Keys that aren't config options, non-header values under `defaults.headers`, and wrongly typed options such as `defaults.timeout = "1000"` are now type errors. Migration: drop casts like `defaults.headers as unknown as HeadersDefaults`, and move custom data off `defaults`. (**#72**)
- **`FaxiosRequestHeaders` declares the Accept-Encoding shortcuts, not Content-Encoding:** the `headers` argument of `transformRequest` (typed `FaxiosRequestHeaders`) now has `getAcceptEncoding`, `setAcceptEncoding` and `hasAcceptEncoding`, which faxios has always registered at runtime but the type didn't declare, so calling them was a type error. `getContentEncoding`, `setContentEncoding` and `hasContentEncoding` are removed from the type. They were never registered, so any call threw `TypeError: ... is not a function` at runtime. Migration: use `headers.get("Content-Encoding")`, `headers.set("Content-Encoding", value)` and `headers.has("Content-Encoding")`. (**#74**)
- **Header `rewrite` is typed `boolean`:** the `rewrite` argument of `FaxiosHeaders#set`, the `set<Header>` accessors (`setContentType`, `setAuthorization`, …) and the matching `FaxiosRequestHeaders` methods no longer accepts a function. The types advertised `(value, name) => boolean`, but `set` never called it, so passing one behaved like `false` and left an existing header unchanged. Passing a function is now a type error. Runtime behavior is unchanged. Migration: pass `true` to overwrite, `false` to keep an existing value, or omit it for the default. (**#75**)
- **Interceptors are removed:** `faxios.interceptors`, `instance.interceptors`, the `FaxiosInterceptorOptions`, `FaxiosInterceptorFulfilled`, `FaxiosInterceptorRejected` and `FaxiosInterceptorHandler` types, and `transitional.legacyInterceptorReqResOrdering` are gone. Use `.use()` middleware instead; one middleware covers both sides of a request. Passing `legacyInterceptorReqResOrdering` now throws `ERR_BAD_OPTION` ("Unknown option"). Request interceptors ran last-registered-first, while middleware runs in registration order on the way in, so reverse the order when migrating several request interceptors. `runWhen` becomes an `if` in the middleware, and `synchronous` has no equivalent. Migration: `api.interceptors.request.use(config => { config.headers.set("Authorization", token); return config; })` becomes `api.use(async (ctx, next) => { ctx.config.headers.set("Authorization", token); return next(ctx); })`, and `api.interceptors.response.use(onOk, onError)` becomes `api.use(async (ctx, next) => { try { return onOk(await next(ctx)); } catch (err) { return onError(err); } })`. (**#89**)
- **`use()` closes five ways a plugin could be typed but missing at runtime:** `next` is now `FaxiosNext<TOptions, TCapabilities>` and takes the context type the middleware received, so `next({ ...ctx, capabilities: {} })` is a type error instead of silently dropping capabilities later middleware needs. `FaxiosContext`, `FaxiosNext` and `FaxiosMiddleware` default their type parameters to `{}` (matching a plugin-free instance) instead of `unknown`. `use()` now rejects, as type errors, a plugin with a required request option (nothing sets it, so it was `undefined` at runtime), required or provided capability names that aren't strings or are `__proto__`/`constructor`/`prototype` (`use()` registers only the other string names), and a union of required or provided capability maps (`keyof` of a union is `never`, so nothing was checked). A nullish `provides` now adds no capabilities instead of collapsing the instance's capabilities to `never`. Runtime behavior is unchanged. Migration: make plugin options optional; annotate a standalone `next` as `FaxiosNext<TOptions, TCapabilities>` to match its `ctx`; type middleware stored in a plugin that provides capabilities as `FaxiosMiddleware<TOptions, TRequires & TProvides>`, not a bare `FaxiosMiddleware`. (**#104**)
- **Plugins are typed with one object, and the plugin API moved to subpaths:** `FaxiosPlugin<TRequires, TProvides, TOptions>` is now `FaxiosPlugin<{ requires?; provides?; options? }>`, so a plugin names the slots it fills instead of passing `unknown` for the others (`FaxiosPlugin<{ options: RetryRequestOptions }>`); any other key is a type error. `authBearer`, `retry` and `timing` and their types (`AuthBearerCapability`, `RetryOptions`, `RetryRequestOptions`, `TimingEvent`) are no longer root exports, and `faxios.plugins` is gone: import each from its own subpath, `@gcmdev/faxios/plugins/auth-bearer`, `/plugins/retry` or `/plugins/timing`. `@gcmdev/faxios/plugins` exports only `definePlugin`, and the root exports nothing plugin-specific besides the `FaxiosPlugin`/middleware types. The `Faxios` class no longer has `use()` or `eject()`, at runtime or in its type, because they checked no capabilities there; register middleware on `faxios.create()` instances or the default export, whose `use()` is typed. Migration: `FaxiosPlugin<unknown, Auth>` becomes `FaxiosPlugin<{ provides: Auth }>` (or build it with `definePlugin` from `@gcmdev/faxios/plugins`); `import { retry } from "@gcmdev/faxios"` and `faxios.plugins.retry` become `import { retry } from "@gcmdev/faxios/plugins/retry"`; `new Faxios(config).use(mw)` becomes `faxios.create(config).use(mw)`. (**#105**, **#107**)
- **`authBearer` keeps explicit headers and only sends the token to the API's origin:** a request that already has the header (per request or from the instance defaults, including `false`/`null`) keeps it, and `getToken` isn't called; `authBearer(getToken, { overwrite: true })` replaces it. The token now goes only to the `baseURL` origin when `baseURL` is absolute, and only to relative request URLs otherwise, so a token installed on the default export or an instance without `baseURL` no longer follows absolute URLs to any host. Protocol-relative URLs (`//host`, `/\host`) count as another origin. `origins: ["https://api.example.com"]` replaces that rule with an allowlist of bare origins. New `scheme` (default `"Bearer"`, `""` for a bare token) and `header` (default `"Authorization"`) options. Options are validated: unknown keys throw `ERR_BAD_OPTION`, bad values `ERR_BAD_OPTION_VALUE`. With `retry` installed before it, every try still asks for a fresh token. The `auth` capability is unchanged. Migration: pass `origins` for an instance that calls several hosts, or `overwrite: true` to keep the old replace-always behaviour. (**#109**)
- **Plugin names and `retry` methods are validated:** `use()` throws `ERR_BAD_OPTION_VALUE` for a plugin whose own `name` isn't a non-empty string (missing, non-string, empty, or only inherited from `Object.prototype`); a capability conflict used to report it as `"undefined"`. Every `retry` `methods` entry, from the plugin or per request, must be an HTTP method token (RFC 9110), so `""` or `"GET POST"` throws `ERR_BAD_OPTION_VALUE` instead of never matching. `retryOn` decides only within `methods`: a method not listed is never retried and `retryOn` isn't asked, so retrying POST with a custom `retryOn` needs POST in `methods` too. (**#124**)

### Features

- **`isSchemaValidationError` narrows by error code:** the guard now returns `SchemaValidationError`, a union discriminated on `code`. After `err.code === FaxiosError.ERR_BAD_RESPONSE_SCHEMA`, `err.response` is required, and `err.response.data` holds the body the schema rejected (after `transformResponse`, before validation) as `unknown`. For the request, params and path-params codes, `response` stays optional. `code` is now typed as the four schema codes instead of `string | undefined`. At runtime the guard also returns `false` for an `ERR_BAD_RESPONSE_SCHEMA` error unless its `response` has `data`, a numeric `status`, a string `statusText`, and object `headers` and `config`. Errors thrown by faxios always pass. `SchemaValidationError` is exported. (**#53**)
- **`isFaxiosError` and `isCancel` are type guards:** `isFaxiosError<T = unknown, D = unknown>(payload: unknown): payload is FaxiosError<T, D>` and `isCancel(value: unknown): value is CanceledError`, both as named exports and on the instance. A `catch (e)` block can now read `e.code`, `e.response?.status` and `e.config` after `if (isFaxiosError(e))` without a cast or `instanceof`. `FaxiosError` takes the same optional `<T, D>` parameters to type `response.data` and `config.data`, so `isFaxiosError<ApiError>(e)` types `e.response?.data` as `ApiError`. That type argument is not checked at runtime. Both guards still test a brand (`isFaxiosError === true`, `__CANCEL__`), not `instanceof`, so errors from another copy of faxios still match. Runtime behavior is unchanged. (**#76**)
- **`.use()` middleware:** instances take onion-style middleware, `api.use(async (ctx, next) => { …; const response = await next(ctx); …; return response; })`. Middleware runs in registration order before the request and in reverse order after it, can change `ctx.config` (its `headers` is a `FaxiosHeaders`, and middleware may assign another `FaxiosHeaders` to it), change or replace the response, catch errors from inner middleware and dispatch, or return a response without calling `next` to skip the request. Each `next()` sends its own copy of the config, so a middleware can call it again to retry from the same input. `ctx.state` is a fresh null-prototype object per request. If the caller aborts, the request rejects with `CanceledError` straight away, even while a middleware is still awaiting something, and an already-aborted request runs no middleware. A plugin's `name`, `middleware` and `provides` count only as its own properties, so a polluted `Object.prototype` can't add middleware or capabilities. `use()` also takes a plugin, `{ name, provides?, middleware }`: `provides` values appear on `ctx.capabilities` for every request, and two plugins providing the same key throw `ERR_BAD_OPTION`. `use()` returns the instance for chaining; `api.eject(middlewareOrPlugin)` removes one by reference and doesn't affect requests already running. `create()` children don't inherit the parent's middleware. New exported types: `FaxiosContext`, `FaxiosNext`, `FaxiosMiddleware`, `FaxiosPlugin`. (**#88**)
- **Typed `.use()` plugins:** `FaxiosInstance` takes two type parameters, `FaxiosInstance<TOpts = {}, TCaps = {}>`, and `use()` returns the instance typed with what the plugin adds. A `FaxiosPlugin<{ requires?; provides?; options? }>` adds `options` to every config-taking member (the callable, `request`, the method aliases, `getUri`, `defaults`, and `define()`/`route()` configs and endpoint calls) and `provides` to `ctx.capabilities`. So after `api.use(cache())`, `api.get(url, { cache: { ttlMs: 30_000 } })` type-checks, and without the plugin it's an excess-property error. Installing a plugin before the capabilities it requires, or after a plugin that provides the same name with an incompatible type, is a type error whose message names the missing capability (`"faxios: install a plugin that provides this capability first": "auth"`). Inside a plugin, `ctx.config` has its own options and `ctx.capabilities` has its required and provided capabilities; plain middleware registered later sees everything installed before it, and with no plugins installed `ctx.capabilities` is `{}`, so `Object.keys(ctx.capabilities)` works without narrowing. `create()` children start untyped, and `eject()` doesn't narrow the type. Excess-property checks only run on object literals, so a config held in a variable can carry a plugin option without the plugin. Declaring `provides` in a plugin's type makes its `provides` value required, so a plugin can't claim a capability it never supplies. `definePlugin({ name, provides?, middleware })`, exported from `@gcmdev/faxios/plugins`, builds a plugin and infers all three slots: `provides` from the `provides` value, `options` and `requires` from the middleware's `ctx: FaxiosContext<Options, Capabilities>` annotation (capabilities the plugin provides itself aren't required), and a `provides` value that contradicts that annotation is a type error. `FaxiosPlugin` and `definePlugin` are the plugin API; the helper types `use()` infers through, and the `"~plugin"` type marker, are internal. `PerCallConfig`, `DefinedEndpoint` and `RouteBuilder` take a trailing `TOpts = unknown` type parameter. (**#90**, **#107**)
- **Built-in plugins:** three plugins for `use()`, each exported from its own subpath (`@gcmdev/faxios/plugins/auth-bearer`, `/plugins/retry`, `/plugins/timing`) and built with `definePlugin`. `authBearer(getToken, { overwrite, scheme, header, origins })` sets `Authorization: Bearer <token>` on requests to the API's origin that don't already carry the header (`getToken` may be sync or async and is called each time) and provides the `auth` capability, so a token-refresh plugin can require it. `retry({ attempts, retryOn, delay, methods })` retries `ERR_NETWORK`, `ETIMEDOUT` and 5xx responses by default, never a cancellation, and only for idempotent methods (GET, HEAD, OPTIONS, PUT, DELETE, QUERY) unless `methods` adds others such as POST; `attempts` counts every try (default 3; an integer of at least 1, otherwise the request rejects with `ERR_BAD_OPTION_VALUE` before anything is sent) and `delay` defaults to 100ms doubling. A per-request `retry: false` turns it off and `retry: { … }` overrides it; an abort during the backoff rejects with `CanceledError` and sends nothing more, and a stream body (web `ReadableStream` or a Node stream) is never retried. `timing(onTiming)` reports `{ config, durationMs, status }` or `{ config, durationMs, error }` once per request and leaves the response unchanged. (**#91**, **#107**, **#109**)

### Fixes

- **`maxDepth` and `env.Request: null` / `env.Response: null` type-check:** `formSerializer.maxDepth` and `paramsSerializer.maxDepth` were honoured at runtime but missing from `SerializerOptions`, and `env.Request`/`env.Response` rejected the documented `null` that disables a constructor for an incompatible custom `fetch`. Both are now in the public types. (**#25**)
- **`options`, `purge`, `link` and `unlink` header groups no longer leak onto the wire:** these method header groups were applied correctly but never removed, so every request also sent a literal header such as `options: [object Object]`. All twelve method header groups are now stripped before the request is sent.
- **`env.FormData` accepts the runtime's `FormData`:** `faxios.create({ env: { FormData } })` and per-request `env: { FormData }` failed strict TypeScript with the DOM lib, because `env.FormData` was typed `new (...args: unknown[]) => object` and the DOM constructor's typed parameters can't accept `unknown`. faxios only ever calls it with no arguments, so it is now typed `(new () => object) | null`. That accepts the DOM and Node/undici `FormData`, subclasses such as `class CustomFormData extends FormData {}`, and `null`, which falls back to the global `FormData` as it already did at runtime. A constructor with required parameters is now a type error, since faxios never passes any. (**#73**)
- **Aborting during pre-flight schema validation no longer sends the request:** if the signal aborted while `pathParamsSchema`, `paramsSchema` or `requestSchema` validation was still awaiting, faxios called `fetch` anyway with a signal that never aborted, so the request went out and the caller only got `ERR_CANCELED` after the response arrived. faxios now checks the signal again right before calling the adapter, and the adapter aborts straight away when it is handed a signal that is already aborted. (**#86**)

### Documentation

- **Docs site on GitHub Pages:** the documentation now lives at https://adrianbrowning.github.io/faxios/ and deploys when a release is published. The npm README is a short overview that links to it, and `homepage` in `package.json` points there. The site is English-only for now. It adds pages for `define()`, `route()` and schema validation, removes the Adapters page and `adapter` option (faxios has no adapter selection), and replaces the `axios-mock-adapter` testing guidance with mocking through `env.fetch`. (**#26**)
- **Docs examples are type-checked and run in CI:** the js/ts blocks in the npm README and the English docs pages are extracted with `mdcode-ts`, type-checked under strict TypeScript against the built package, and run against a fake `fetch` (`pnpm run test:docs-examples`). Currently 139 blocks are type-checked and 125 of them run. Examples now import `@gcmdev/faxios`, use the Faxios type names, and no longer show APIs faxios doesn't have (`CancelToken`, `require()`, `isAxiosError`). Blocks opt out with `check=types` (type-check only) or `check=skip`. (**#25**)
